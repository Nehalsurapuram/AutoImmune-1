# AutoImmune

AutoImmune is a B.Tech research prototype: a hybrid self-healing pipeline for a Java Spring Boot service (order-service). It observes the service, detects and diagnoses a fault, drafts three candidate patches, and validates each one in a Docker sandbox through four gates (V0 compile, V1 target test, V2 full test suite, V3 new Semgrep findings). A rule-based risk tier then decides to REJECT, ESCALATE or AUTO_APPLY. Auto-applied patches are deployed, watched over a health window, and either promoted or rolled back, with evidence recorded for every candidate. The research question is how much execution evidence lets an AI-generated patch deploy without human review, and what each gate catches.

## Pilot status (2026-11-08)

> Every number here comes from `results/pilot_report.md`, generated by `python analyse.py` from
> `results/evidence.jsonl` (101 rows, sha256 `c1d8935cb597…`). `python analyse.py --check` fails if the report is out
> of date. These are pilot counts, not inferential claims. See [docs/audit/AUDIT_BASELINE.md](docs/audit/AUDIT_BASELINE.md).

- **Scripted candidates (mechanism checks, not AI results):** 16 hand-built patches (5 each for F01 and F04, 6 for F06)
  gated in Docker. By the kind each was built as, V1 stopped the 3 `ineffective` patches, V2 the 3 `regressive`
  ones, and V3 the 3 `insecure` ones. (In the live-diagnosis run, F06 `insecure` stopped at V2 with a Docker tool
  **error**, recorded as an error, not as a pass.) `overfitting` patches passed every gate in all three faults.
  They were auto-applied in F01 and F06, and in F04 they were auto-applied or escalated depending on the diagnosed
  file. This is the gap an independent oracle has to measure.
- **No independent labels yet:** `labels.json` and `hidden_tests/` do not exist, so unsafe-deployment rate (UDR),
  unsafe escape and false-rejection rate (FRR) are all n/a. The `candidate_kind` names above are builder intent,
  not ground truth.
- **Live LLM patches:** 17 attempts. `qwen2.5-coder:7b` applied 0/9. `qwen2.5-coder:1.5b` applied 3/8, and those
  3 then failed the target test (V1). No live patch passed V1 and none was deployed. The two 1.5b runs that applied
  were made with code that was never committed (audit F-24), so they cannot be reproduced from this repository.
- **End-to-end runs with provenance (S1):** full runs on F06, F01 and F04 (code `f5ef81a`, each recording its git
  state). The fault was detected 5.0 s, 5.0 s and 6.0 s after the faulty build went live. Every step artifact was
  written and the healthy baseline restored.
- **Deployment:** 6 promotions after a passing health window. Three of them were the F06 `overfitting` patch, picked
  because it was the smallest diff: a passing health window is not evidence of correctness.
- **Rollback:** 1 **staged** rollback. The planted `slow` patch passed V0-V3, a probe took 3016 ms against a 2000 ms
  limit, and it was rolled back to the previous image in 4.0 s. 0 real (unplanned) rollbacks.
- **Human review:** 2 real `human_cli` decisions on the escalated F04 config patch: one reject (2026-11-07) and one
  approve, which was then deployed and promoted (2026-11-08).

## Setup and tests

Needs Python 3.12 and Docker Desktop running (the gates use the `maven:3.9-eclipse-temurin-17` and
`semgrep/semgrep:1.100.0` images). Do not copy a `.venv` between machines; create it fresh:

```
py -3.12 -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
.\.venv\Scripts\python -m pytest -rs              # full suite (~10 min with Docker)
.\.venv\Scripts\python -m pytest -m "not docker"  # fast suite, no Docker
```

## Regenerating results

```
.\.venv\Scripts\python analyse.py           # rewrites results/*.csv and pilot_report.md (old ones archived)
.\.venv\Scripts\python analyse.py --check   # exit 1 if results/ is stale
.\.venv\Scripts\python tools\audit_baseline.py --out docs\audit\baseline_manifest.json
```
