# AutoImmune

AutoImmune is a B.Tech research prototype: a hybrid self-healing pipeline for a Java Spring Boot service (order-service). It observes the service, detects a fault with rule-based checks, and localises it. In live mode a model diagnoses it. In rule mode the pipeline uses the top application stack frame; incidents with no stack trace (F04 health DOWN, F06 probe mismatch) instead take the file named in `faults/<id>/fault.json` (oracle localisation, flagged `oracle_localisation=true` in diagnosis.json and excluded from localisation hit rates). Candidate patches come next: in live mode the model is asked for three (one early run returned two); scripted runs read every hand-built candidate for the fault (5 for F01 and F04, 6 for F06). Each candidate goes through up to four gates, in order, stopping at the first failure: V0 the patch applies and compiles, V1 the target test passes, V2 the existing test suite passes, V3 no new Semgrep findings compared with the unpatched faulty code. The apply check runs on the host; the Maven and Semgrep steps run in a network-isolated Docker container. A rule-based risk tier then decides to REJECT, ESCALATE or AUTO_APPLY. In each full run one candidate is deployed: the AUTO_APPLY candidate with the smallest diff or, if there is none, an ESCALATE candidate that a human approves. It is watched over a health window and then promoted or rolled back to the previous image. Each completed run records one evidence row per candidate; runs that fail or are interrupted record none and are listed in the run ledger. The research question is how much execution evidence lets an AI-generated patch deploy without human review, and what each gate catches.

## Results (pilot, 2026-11-09)

> Counts and rates come from `results/pilot_report.md`, generated by `python analyse.py` (checked by
> `python analyse.py --check`); independent labels come from `tools/oracle.py`. Detection times, smoke tests and
> image-ID checks are read from run artifacts (`runs/<run_id>/incident.json`, `faulty_deploy.json`, `deploy.json`,
> `rollback.json`). `results/` and `runs/` are local and not in git. These are pilot counts on three seeded
> faults, not general safety claims. Full write-up: [docs/PROJECT_REPORT.md](docs/PROJECT_REPORT.md).
> Baseline integrity audit (DRAFT, 2026-11-08; covers the earlier 79-row evidence, before the oracle and live-AI runs;
> independent sign-off pending): [docs/audit/AUDIT_BASELINE.md](docs/audit/AUDIT_BASELINE.md). Current acceptance
> status: [docs/audit/acceptance.json](docs/audit/acceptance.json).

- **Full loop, with provenance:** on F06, F01 and F04 the detector raised an incident 5–6 s after the faulty build
  first answered HTTP (two failed checks 5 s apart; container start-up comes before that). The chosen candidate was
  then gated, decided, deployed and promoted or rolled back. The five most recent deploys (three live AI runs, the
  staged rollback and the human-approved F04 run) were smoke-tested side by side and image-ID verified; the 7 earlier
  scripted deploys predate both checks. Each run records its code hash; some scripted runs and the healthy watch ran
  with uncommitted changes, marked `+uncommitted` in the run ledger. There was no false alarm in 300 s of healthy
  traffic.
- **Independent oracle:** every candidate is labelled offline (45 distinct diffs: 16 hand-built, 29 AI). A diff that
  does not apply is labelled invalid with no further tests (18 distinct AI diffs, 21 of 32 AI attempts) and is not
  counted as safe or unsafe. The other 27 are judged by hidden specification tests, a hidden performance test, the
  full existing suite and a security probe. The pipeline never sees the hidden tests, the probe or the labels; the full
  existing suite is the same one gate V2 runs, and the probe overlaps with V3. Two-person review of the labels is
  pending.
- **Hand-built patches (32 units = 16 patches × 2 diagnosis modes, collapsed from 95 recorded evaluations; 26 unsafe
  by oracle):** unsafe units that would be auto-applied fell from 20 (target test only) to 13 (plus full suite) to 7
  (full AutoImmune policy). 0 of 6 correct-patch units (3 patches, one per fault) were rejected; under the full policy
  4 were auto-applied and the 2 F04 units were escalated.
- **Real AI repair:** `openai/gpt-oss-120b` diagnosed F06, wrote a fix that passed all gates, and the fix was
  **deployed and promoted automatically**. The oracle labels it correct.
- **Key finding:** under the full policy, 5 AI patches were decided AUTO_APPLY and **2 of them were wrong** per the
  oracle. Only one patch per run is deployed, so 3 were deployed and promoted, and 2 of those 3 were wrong:
  - F01: the patch only rejects `null`, so blank names still slip through.
  - F04: after a misdiagnosis, the patch forces the health check to UP. The correct config fix was escalated and never
    reached a human.

  Passing tests and health checks is not proof of correctness.
- **Rollback:** a planted slow patch passed every gate and the side-by-side smoke test, then breached the latency
  limit and was rolled back automatically in 5.1 s, with the restored image ID verified
  (`runs/f06-rule-scripted-20261108t201808z`; staged demo, never counted as a real catch).
- **Human review:** three real `human_cli` decisions are recorded, all on the hand-built F04 config patch (scripted
  `correct.diff`, escalated because it touches application.properties): one reject (2026-11-07) and two approvals
  (2026-11-08), both deployed and promoted. No AI-drafted patch has received a human decision.
- **Limits:** three development faults, no held-out set, small samples. Policy differences are not statistically
  established. In rule mode, F04 and F06 localisation is oracle localisation from `fault.json`, and it also feeds the
  decision's scope rule for those 11 scripted units. Promotion means the health window passed, not that the patch is
  correct.

## Setup and tests

Needs Python 3.12. The pipeline and the 16 `docker`-marked tests also need a running Docker daemon (Docker Desktop on
Windows) with the `maven:3.9-eclipse-temurin-17` and `semgrep/semgrep:1.100.0` images pulled and the `autoimmune-m2`
Maven cache volume populated once with network access (the gates run Maven offline against it). Without these the
Docker tests are skipped (shown by `-rs`). The fast suite needs no Docker. Do not copy a `.venv` between machines; create it fresh:

```
py -3.12 -m venv .venv
.\.venv\Scripts\pip install -r requirements.lock
.\.venv\Scripts\python -m pytest -rs              # full suite (~10 min with Docker)
.\.venv\Scripts\python -m pytest -m "not docker"  # fast suite, no Docker
```

.\.venv\Scripts\python analyse.py           # rewrites results/*.csv and pilot_report.md (old ones archived)
.\.venv\Scripts\python analyse.py --check   # exit 1 if results/ is stale
